# 冗余预取与有上限的距离缓存

仓库附带的历史结果：[逐查询指标](docs/benchmarks/redundancy/metrics.json)、[内存测量](docs/benchmarks/redundancy/memory_probe.json)、[对比图](docs/benchmarks/redundancy/comparison.png)。下文 `results/...` 表示重新运行实验时生成的本地路径。

## 结论

已实现并测试“首次多取候选，减少不足后重查”，同时不保存全库已计算距离。新 CLI 默认 `bounded`，首次 512 个，缓存上限 8192 个。

首次 512 个使需要扩充的查询从 6/14 降到 1/14；与同一缓存实现的 128 配置相比，P95 改善，中位耗时有所增加。首次 2048/4384 消除了本批扩充，但总体更慢。因此不是初始冗余越多越好。

## 1. 怎样限制距离存储

新接口为 `DiverseIndex.search_bounded`：

1. 原有三级路由只提供长段处理顺序，不用近似路由排除未访问区域。
2. 完整核验按长段分块进行，默认每块最多 16,384 个起点。
3. 每块产生的距离立即与紧凑候选数组合并，只保留当前全局最好的 M 个。
4. 候选只包含 `float64 distance + int64 sid + int64 start`，共 24 字节/条；只为最终 K 个结果构造来源字段与可选曲线。
5. 淘汰的距离在处理完该块后释放，不保留历史距离；扩充时重新计算，没有 N 项距离表。
6. 先取 512，不足时乘四扩大，但不会超过 `max_candidates=8192`。达到上限仍不足且未穷尽时返回未完成标记。

保留的候选距离/位置数据空间为 **O(M)**，连同块距离、合并/排序工作数组，为 **O(M+B)**。M 为候选上限，B 为块大小。合并时有临时数组，因此不是“总内存等于候选数组的大小”。

这是针对**查询距离缓存**的限制。现有符号索引、原始数据、O(N) 的均值/标准差缓存，以及路由中命中块的投票字典，仍有原来的内存成本。总体引擎内存不是 O(M+B)，不能声称整个数据库只占几百 KiB。

## 2. 同一批查询对照

1,023,529 个合法起点，七类数据各两个原片段查询，共 14 个，长度 244，随机种子 20260921。返回 K=10，同源片段起点间距至少 244。轮换方法执行次序减少固定顺序偏差；耗时包括常驻 API 和 JSON 序列化，不包括初始化、网络或穷举审计。

| 方法 | 中位 ms | P95 ms | 最慢 ms | 需要扩充的查询 | 最大轮数 | >100 ms |
|---|---:|---:|---:|---:|---:|---:|
| 旧实现，128 起步 | 110.61 | 172.73 | 180.19 | 6/14 | 3 | 8/14 |
| 新缓存，128 起步 | **77.51** | 139.78 | 144.28 | 6/14 | 3 | 5/14 |
| **新缓存，512 起步（默认）** | **87.39** | **130.51** | **137.29** | **1/14** | **2** | **5/14** |
| 新缓存，2048 起步 | 108.57 | 150.63 | 166.26 | 0/14 | 1 | 8/14 |
| 新缓存，4384 起步 | 142.10 | 183.25 | 197.15 | 0/14 | 1 | 11/14 |

全部五种配置的 14 次查询均返回十个不重叠片段，逐轮距离均与“排除已选邻域后的全库最近邻”一致，即该定义下审计正确率为 100%。距离并列允许不同位置。没有将普通 Top-10 集合当作去重目标。

128 配置中位最快；512 配置更少重查、P95 更低，故选 512 为折中默认值。14 个查询是小样本，不能据此断言其他数据集或设备必然同样最优。

新旧 128 的差异包括候选存储与分块合并的实现优化；要判断单纯增加初始候选的影响，应比较四个“新缓存”配置，而不是将所有提速归因于冗余。

## 3. 内存证据

候选数组自身：

| 候选条数 | 距离/位置数组净大小 |
|---:|---:|
| 512 | 12 KiB |
| 2048 | 48 KiB |
| 4384 | 102.75 KiB |
| 8192（默认上限） | 192 KiB |

最大单块 16,384 个 float64 距离为 128 KiB，此外还有位置、合并、排序和路由临时数组。本批内部统计的数值数组峰值约 480 KiB（128/512/2048 配置）或 735.5 KiB（4384 配置）；这是已计数缓冲区的大小，不是完整内存峰值。

另外，对原 GPU 查询，在索引初始化后开启 `tracemalloc` 测量查询增量峰值：

| 初始候选 | 增量跟踪峰值（字节） |
|---:|---:|
| 128 | 809,300 |
| 512 | 799,001，约 0.76 MiB |
| 2048 | 1,102,176 |
| 4384 | 1,286,880 |

该测量包含 Python 和可被追踪的 NumPy 分配，排除初始化前已驻留索引，不是进程 RSS，未被追踪的本地库分配可能不在内。没有把均值/标准差缓存计入这项增量。

基准程序为验证正确性，会在**独立审计代码**中生成全库距离；这些数组不进入查询引擎，也不计入查询延迟。独立的 `probe_query_memory.py` 不生成这类审计数组，因此不会将审计所用的 O(N) 空间误认为查询缓存。

## 4. 上限与完整性

- `complete=true, certified=true`：已补足 k 条，或已证明满足条件的候选确实耗尽。
- `candidate_limit_reached=true, complete=false, certified=false`：达到缓存上限，但还不能证明全库已无更多非重叠结果。
- `exhausted=true`：全库或距离阈值内候选确实不足 k 条；不等同于达到缓存上限。

新增测试用连续常量序列制造大量重叠近邻：上限仅十条时必须报告未完成；4384 条时可补齐十个非重叠结果并通过穷举核验。另保留跨内部数据块、不同列独立排除、随机非原查询、阈值无结果和 64 位位置测试。共三项测试通过。

## 5. 时间复杂度有没有降低

设 R 为实际扩充轮数、N 为合法起点数、D=48、m=244、M 为最多保留的候选数、B=16384、G≈N/B。

主要扫描与原始核验开销仍是：

```text
O(R × N × (D+m))   最坏数值计算上界
```

预取更多候选使很多查询的 R 从 2/3 降到 1，但单轮阈值更宽、核验与合并成本增加。当前每块用局部选择和最多约 2M 条候选排序合并，还存在约 `O(R × G × M log M)` 的合并开销；另有路由排序和排除区间维护，不能把全部复杂度写成一个纯线性项。

在 M、B、R 固定时，主要扫描随 N 近似线性；路由候选排序仍可能带额外对数因子。**这次主要减少重复轮次与候选存储成本，没有把全库精确检索变为 O(log N)。** 缓存硬上限使扩充轮数有界，但可能以明确返回未完成作为代价，不能同时无条件承诺固定内存和任意数据下返回足够结果。

## 6. 使用与复现

```powershell
python diverse.py --query-json ../results/query.json --strategy bounded --initial-candidates 512 --max-candidates 8192 --output results/bounded_query.json
python benchmark_redundancy.py
python probe_query_memory.py
python -m unittest -v test_diverse.py
```

Python：

```python
result = engine.search_bounded(
    query, k=10, min_separation=244,
    initial_candidates=512, max_candidates=8192,
    include_values=True,
)
```

结果文件：`results/redundancy/metrics.json`、`comparison.png`、`memory_probe.json`。默认命令行已切换到 `bounded`；旧的层级查询可能保留大量距离，要求本次缓存限制时不要使用旧 `search` 方法。

当前测试仍只覆盖约百万起点的开发库，没有百亿点验证，也没有全部查询低于 100 ms 的保证。
